**Codex review of #894 (both P2 fixed, switch 1 only).**
- Each radius-2 grid is lit only in line of sight (`borg_los`), the way the
  engine's `add_light` tests `los()` per grid. The first version gated (2,1)
  on (2,0) being floor, C's proxy, so it missed (2,1) behind a wall at (2,0)
  and lit (2,0) behind a wall at (1,0).
- The dark frontier counts each ray's lit steps by engine distance
  (`lit_steps`): with a lantern, the diagonal ray has one lit step and its
  first dark grid is (2,2), not (3,3). At switch 0 it still counts the radius
  on every ray, consistent with C's shape, which lights (2,2).
- New tests: `lit_steps_follow_the_engine_distance`, plus the frontier's
  radius-1 rays with the engine shape.

**Codex re-review of #894 (radius-2 line of sight, partly resolved).**
- The finding: `borg_los` reuses the walk test, so light passed known passable
  rubble, which the engine's `los()` blocks: rubble has neither `LOS` nor
  `PROJECT` in terrain.txt.
- The fix: `borg_los_light` (`borg_projection.rs`, now in `HOOKED`) runs the
  same line algorithm through a light test. A grid passes light only when it
  is known and projectable: floor or a trap, an open or broken door, stairs, a
  shop, lava. Unknown terrain blocks it. This is conservative: when the map
  hides an open path, the Borg marks fewer grids lit than the engine. That is
  the safe direction, because it keeps the monster record (#877).
- Test: `light_does_not_pass_rubble_the_walk_test_crosses`, the reviewer's
  rubble case.
- Not changed: the Borg's view (`BORG_VIEW`, `borg_cave_view.rs`) also treats
  passable rubble as floor. That is C's view code at both switch values, and
  out of this PR's scope. The reviewer mentions it, and it can make
  `borg_follow_kill_aux` expect a monster visible behind rubble on a grid lit
  some other way.
